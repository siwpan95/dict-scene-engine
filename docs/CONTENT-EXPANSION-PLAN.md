## 2. 调研依据（联网，含来源）

### 2.1 规模基准

| 来源 | 基准 | 我们的位置 |
|---|---|---|
| [Literotica 发布门槛](https://www.literotica.com/faq/interactive-stories/interactive-story-games-publishing-rules) | 最低 20 knot / 40 选项 / 1000 词 | **刚触及最低门槛** |
| [Choice of Games 长度标准](https://www.choiceofgames.com/2017/07/length-and-coding-efficiency/) | 总量 ≥ 10 万词、单周目 ≥ 2 万词、**单周目/总量 = 0.2–0.4** | 差约两个数量级 |
| Inkle《80 天》 | 60 万字 / 1000+ 分支 / 150 城市 | 商业长篇参照 |
| Inkle《巫术》四部曲 | 150 万字 / 35000 分支 | 商业长篇参照 |

> 比值含义：**< 0.2** 表示大量内容玩家永远看不到；**> 0.6** 表示选择基本不影响体验（每局雷同）。

### 2.2 结构模式（[Ashwell 分类学](http://www.gamedesign.gg/articles/branching-dialogue-systems)）

| 模式 | 成本曲线 | 适用 |
|---|---|---|
| Time cave（纯分支不汇合） | 指数 | 仅短篇 / 结局处 |
| Gauntlet（单主干 + 短分支） | 线性 | 线性叙事要张力 |
| **Branch-and-bottleneck（局部分支 → 状态 → 瓶颈重汇）** | **近似线性** | **商业主力，本项目主干采用** |
| Quest structure（内容附着于地点） | 线性 | 探索段 |
| Open map / quality-based（内容池 + 需求条件） | 长尾极便宜 | 重复内容、Phase 3 |

### 2.3 内容质量做法（[来源](https://dunia.gg/blog/pick-your-own-adventure-story)）

- **加载式选择**取代空洞选择（见 §6.3）
- 重汇要"**复用情节节拍，不复用情绪状态**"——分支带着不同历史回到同一节点
- **fail-forward**：失败也推进，记录代价，不卡死
- 全局标志保持 **5–10 个**，多了会淹没在条件里

### 2.4 组织方法（[Ink 实践](https://pulsegeek.com/articles/ink-language-scripting-tips-and-examples)）

- knot（场景）+ stitch（场景内事件）分层 → 本项目用 **ID 命名前缀**模拟
- 用变量/条件替代复制文本（"同一场景支持多种结局而不复制大段对话"）
- 房间-对象模式：对象交互后回房间枢纽 = 自然探索循环
- **叙事账本**：集中记录所有变量、触发条件与预期结果

## 5. 主线规划：《古堡寻剑》扩写（17 → 25 场景）

### 5.1 结构

**Branch-and-bottleneck 为主干 + 村庄枢纽可重访**

```
                      ┌─ 林间线（forest.*）──┐
   序章 village 枢纽 ─┼─ 官道线（road.*）────┼→ 瓶颈 castle.gate（读状态）→ 古堡内部 → 终章多结局
   （可重访）         └─ 情报线（gossip.*）──┘
                      └─ 试炼场（arena.*）───┘（支线，随时可回）
```

瓶颈节点 `castle.gate` 读取三组状态决定进入方式：
- `items.rusty_sword` 或其他武器 → 亮剑直入
- `flags.intelBought`（情报）→ 知晓守卫换班，潜入
- 两者皆无 → 只能徒手闯（高难）

## 6. Mod 题材选型

### 6.1 对比

| 维度 | 侦探调查 | 城镇经营 |
|---|---|---|
| 枢纽辐射适配 | ★★★ 天然（案卷桌 = hub，线索 = spoke） | ★★（经营面板 + 事件队列） |
| 现有引擎支撑 | **零改动**（知识标记 = flags，询问 = 条件选项） | 需新增经营 mode 插件（回合推进、资源结算界面） |
| 状态设计 | 简单事实 + 链式事实（Ink 已验证的模式） | 数值经济系统 + 随机事件 |
| 文字产出比 | 高（对话驱动） | 中（界面与数值占篇幅） |
| 重玩价值 | 高（多凶手、多结局） | 高（不同经营路线） |
| 风险 | 低（逻辑一致性靠 flag，可用校验器守住） | 中（平衡性需反复调） |

### 6.2 推荐：**侦探调查**

理由：① 零引擎改动，Phase 1 可专注内容；② 知识标记与本项目 `flags` 一一对应，是 hub-and-spoke 最纯粹形态；③ 对话驱动，单位工作量的字数产出最高；④ 逻辑风险可用 §8 的校验器兜住。

城镇经营列为 **Phase 2 备选**——届时引擎已有 mode 扩展点实践（战斗模式），经营模式是自然延伸。

### 6.3 Mod 场景清单：《星港迷案》（15 场景）

题材与现有 `starport.js`（星港 DLC）世界观复用，作为独立案件包。

```
                   ┌─ 询问船员（crew.*）──┐
   case.board 案卷桌 ─┼─ 勘察现场（scene.*）──┼→ 指控（accuse）→ 多结局
   （hub，可重访）    ├─ 查阅档案（archive.*）┤
                   └─ 走访区域（district.*）┘
```

| ID | 作用 | 状态变更 |
|---|---|---|
| `case.board` | **案卷桌枢纽**：列出已掌握线索与可行动项 | — |
| `case.brief` | 接案：死者、现场、时限 | `flags.caseAccepted` |
| `scene.dock` | 勘察：码头现场 | `clues.dock`、发现物证 |
| `scene.cabin` | 勘察：死者舱室 | `clues.cabin` |
| `scene.cargo` | 勘察：货舱（需权限） | `clues.cargo`、`flags.cargoAccess` |
| `crew.captain` | 询问：船长 | `testimony.captain`（可能说谎） |
| `crew.engineer` | 询问：轮机长 | `testimony.engineer` |
| `crew.medic` | 询问：随船医生 | `testimony.medic` |
| `archive.log` | 档案：航行日志 | `clues.log` |
| `archive.manifest` | 档案：货物清单 | `clues.manifest` |
| `district.bar` | 走访：酒吧（花钱买消息） | gold−、`clues.rumor` |
| `district.market` | 走访：黑市（需声望） | `clues.weapon` |
| `case.deduce` | 推理台：拼合线索，锁定嫌疑人 | 读线索数，设置 `flags.suspect` |
| `case.accuse` | 指控：选择指认对象 | 决定结局 |
| `ending.truth` / `ending.miscarry` | 真凶归案 / 冤案结局 | 由 `flags.suspect` + 线索完整度决定 |

### 6.4 侦探 Mod 的状态设计（知识标记模式）

```
简单事实（二值）：clues.dock、clues.cabin、clues.cargo、clues.log、clues.manifest
链式事实（渐进）：suspectLevel = 0..3（0 无线索 → 3 可指认）
证词可信度：testimony.captain / engineer / medic（各自 true/false，含谎言标记）
资源：gold（买消息）、rep.starport（黑市准入）
```

## 7. 内容规范

### 7.1 命名空间

```
主线：<章节>.<地点>[.<子场景>]    例：castle.gallery、forest.ruins
支线：<支线名>.*                   例：arena.boss
Mod： <mod前缀>.<类别>.<对象>      例：case.board、crew.captain
结局：ending.<标识>                例：ending.sword、ending.truth
```

### 7.2 文本

- 每场景正文 **150–250 字**（现状 60 → 目标 ~200）
- 场景文本承担：环境描写 + 一个明确的情境问题
- 支持 `{name}` `{hp}` `{gold}` 插值（注：`title` 与 `choice.text` 目前**不插值**，如需"需 10 金币（你有 {gold}）"需先补引擎能力，见 §9）

### 7.3 选择设计（加载式，禁止空洞）

| 场景 | 空洞写法 ❌ | 加载式写法 ✅ |
|---|---|---|
| 前往古堡 | 走林路 / 走官道 | 抄近道（快但遇伏） / 走官道（安全但要打点） / 先摸清守卫换班 |
| 面对守卫 | 战斗 / 逃跑 | 亮出武器威慑 / 贿赂（消耗金币） / 绕行（需情报） |
| 询问证人 | 态度好 / 态度差 | 出示证据施压 / 示弱博同情 / 谎言试探（留后患） |

规则：**每个选项至少有可观察的后果**（一行不同台词 / 一个状态变化 / 一件物品），否则合并为叙述。

### 7.4 状态命名

```
flags.<名词化的事实>   例：flags.intelBought、flags.swordLore
items.<snake_case>      例：items.rusty_sword
数值：<域>.<对象>       例：rep.village、visits.castle、suspectLevel
```

规则：**若某个 flag 不影响后续任何对话/通道/情绪，就删掉**。

## 8. 前置基建（动笔前完成）

### 8.1 `scripts/lint-content.mjs`（内容校验器）

检查项：

| 检查 | 说明 |
|---|---|
| 悬空 goto | 所有 `goto` 目标存在于字典（`@` 前缀免检，但校验白名单） |
| 不可达场景 | 从 entry 出发 BFS，未被访问到的场景报错 |
| 结局可达 | 每个 `ending.*` 至少存在一条可达路径 |
| flag 一致性 | 被引用的 flag 必须在叙事账本声明；声明了但从未被读取的 flag 告警（死标志） |
| 空场景 | 无 `text` 或文本 < 120 字告警 |
| 空洞选项 | 选项既无 `do` 也无 `if` 且 `goto` 与其他选项相同 → 告警（疑似假选择） |
| ID 命名 | 符合 §7.1 命名空间规则 |

接入 `package.json`：`"lint:content": "node scripts/lint-content.mjs"`，并在 e2e 中作为一道断言。

### 8.2 叙事账本

新建 `docs/NARRATIVE-LEDGER.md`：`flags` / `items` / 数值 / 结局的清单，每项标注 **写入处** 与 **读取处**。这是 Ink 与商业叙事团队的标准做法，也是扩容后不失控的关键。

### 8.3 e2e 扩展

- 主线关键路径（默认选择 → 通关）
- Mod 关键路径
- 各结局分支的可达性（至少 1 条路径各跑通一次）
- 枢纽重访幂等性（连续访问同一枢纽，状态不重复累加）
